ImapKit (v__VERSION__)
==========__VBAR__=
ImapKit starts an IMAP server that is suitable for running client
integration tests. Nothing is written to disk, all operations are
performed on memory and the changes are lost after restart, so the
initial state is always guaranteed when running your tests.

Additionally ImapKit offers an incoming SMTP server - every mail
sent to it, is appended to INBOX. To use the incoming SMTP server,
use smtpPort option.

Usage: imapkit [OPTS]

  -p <port>, --port=<port> Port number to listen to, defaults to 143
  -s, --secure=true        Starts a secure server, defaults port to 993
  -d, --debug=true         Writes IMAP traffic to console
  --storage=<path>         Path to JSON file with the directory tree
  --config=<config>        Path to config JSON file
  --script=<path>          Path to a JSON file with script rules that
                           make the server misbehave on purpose (see
                           "Scripted faults" below)
  --plugin=<plugin>        Enables a plugin for the server. See below for
                           available plugins.
  --smtpPort=<port>        Port number for incoming SMTP server. If not set
                           SMTP server is not started.

The options can also be set with environment variables: IMAPKIT_PORT,
IMAPKIT_SECURE, IMAPKIT_DEBUG, IMAPKIT_STORAGE, IMAPKIT_CONFIG,
IMAPKIT_SCRIPT, IMAPKIT_PLUGINS (comma separated) and IMAPKIT_SMTPPORT.

NB! If port or smtpPort values are below 1024 you most probably need to
use sudo or run the command with administrator rights.

Available plugins
-----------------

Usage: imapkit [OPTS] --plugin=ID --plugin=IDLE
or:    imapkit [OPTS] --plugin=ID,IDLE

__PLUGINS__

Configuration files
-------------------

Configuration file takes the following structure

{
    "plugins": ["ID", "IDLE"],
    "debug": false,
    "secureConnection": false,
    "port": 143,
    "maxLiteralSize": 67108864,
    "appendLimit": 5242880,
    "messageLimit": 1000,
    "users": {
        "testuser": {
            "password": "testpass"
        }
    },
    "id":{
        "name": "hoodecrow",
        "version": "__VERSION__",
        "key": "value"
    }
}

Scripted faults
---------------

A script file holds a list of rules. Each rule watches one event
("greeting", "command", "input", "response" or "continuation") and
changes what the server does when its matchers fit. For example, this
script answers the first FETCH with a literal that is too short and
then drops the connection:

[
    {
        "on": "response",
        "command": "FETCH",
        "untagged": true,
        "times": 1,
        "send": "* 1 FETCH (BODY[] {100}\r\nshort",
        "close": true
    }
]

Strings are sent as they are, "$TAG" stands for the command tag and
"match" is a regular expression. See the README for every option.

Storage file is a tree like structure starting with namespace values.
INBOX has its own namespace.

{
    "INBOX":{
        "uidnext": 123,
        "messages": [
            {"raw": "Subject: Test\r\n\r\nHello world!"}
        ]
    },
    "":{
        "separator": "/",
        "folders": {
            "Parent folder":{
                "folders":{
                    "Subfolder": {}
                }
            }
        }
    },
    "#news/":{
        "type": "shared"
    }
}

If no storage file is specified, an empty "INBOX" is used. If no users
are configured, the only account is "testuser" with password "testpass".
The storage and users objects are copied, so the files are never changed.
